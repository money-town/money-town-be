# 소유주 차액 납부 계약 — Asset 구현 및 연동 대기 항목

## 구현 범위

- 단가 = 평가금액 / 전체 지분 수량, 1원 미만 버림.
- 차액 = 평가금액 - 단가 × 전체 지분 수량.
- 자산 등록 시 소유주가 납부 방식을 명시한다. 기존 자산에는 임의로 선택값을 넣지 않는다.
- `SALE_DEDUCTION`: 매각대금에서 차액과 연 10% 단리 이자를 플랫폼 몫으로 공제하는 방식.
- `WALLET_PAYMENT`: 지갑에서 차액 납부, 이자 없음. 이 값을 선택했다고 납부 완료된 것은 아니다.
- 공모 성공 완료 시각과 차액 원금을 Asset DB에 확정한다.
- 자산 등록일이나 청약 개별 성공 시점에는 이자가 발생하지 않는다.
- 한국 날짜 기준 완료일 당일은 경과일수 0일. 기준일 - 완료일로 일수를 계산한다.
- 이자 = 원금 × 0.10 × 경과일수 / 365. 윤년에도 분모는 365, 누적 계산 후 1원 미만 버림.
- 견적 조회는 원금을 줄이거나 납부 완료 상태를 기록하지 않는다.

## 자산 등록 요청 변경

`POST /api/v1/assets`의 기존 요청에 필수 필드 추가:

```json
{
  "ownerBurdenPaymentMethod": "SALE_DEDUCTION"
}
```

지갑 납부를 선택하면 `WALLET_PAYMENT`를 보낸다. `unitPrice`는 요청으로 받지 않는다.
상세 조회 응답에는 `ownerBurdenPaymentMethod`, `ownerBurdenAmount`, `offeringCompletedAt`을 포함한다.

## 공모 서비스 → Asset 성공 완료 통지 (신규 내부 API)

`POST /api/v1/internal/assets/{assetId}/offering-completion`

필수 헤더: `X-User-Role: SYSTEM`

```json
{
  "offeringId": "61d58776-a4ae-4c13-9f17-6f0dc598fa34",
  "completedAt": "2026-09-03T03:00:00Z"
}
```

- 모집 성공과 필요한 확정 처리가 끝난 경우에만 호출한다. 모집 마감/기간 종료만으로 호출하지 않는다.
- `completedAt`은 공모 서비스에 저장된 실제 성공 완료 시각이다. 전송/재시도 시각으로 교체하지 않는다.
- 최초 호출과 동일한 ID·시각의 재시도는 200. 최초 완료 시각은 바뀌지 않는다.
- 다른 공모 또는 다른 시각으로 덮어쓰면 409, 미래 시각은 400, SYSTEM 외 역할은 403.
- 공모 완료 데이터를 DB에 커밋한 뒤 통지하고, 실패 시 동일 내용으로 재전송해야 한다.
- 현재 모델은 자산당 최초 성공 공모 1회만 지원한다. 재공모/추가 발행은 별도 회차별 채무 모델 협의가 필요하다.

## 지갑/정산 → Asset 견적 조회 (신규 내부 API)

`GET /api/v1/internal/assets/{assetId}/owner-burden/quote?asOf=2027-09-03`

필수 헤더: `X-User-Role: SYSTEM`

응답 data 필드:

```json
{
  "assetId": "565c39a4-728e-4ba8-8509-6d1f28051e36",
  "ownerId": "72ffebf8-e8c7-4187-8a69-ea65e00328bc",
  "offeringId": "61d58776-a4ae-4c13-9f17-6f0dc598fa34",
  "paymentMethod": "SALE_DEDUCTION",
  "offeringCompletedAt": "2026-09-03T03:00:00Z",
  "asOf": "2027-09-03",
  "principalAmount": 1000,
  "interestAmount": 100,
  "totalAmount": 1100
}
```

- 공모 완료 전은 409, 완료일보다 이른 기준일은 400.
- 미래 기준일도 예상 견적으로 조회 가능하다. 실제 공제 시에는 정산 확정일을 사용해야 한다.
- 이 응답은 수납 전 견적이다. 이미 납부했는지 여부나 현재 미납 잔액이 아니다.

## 실제 수납을 위해 아직 연결해야 하는 부분

현재 Wallet 내부 API에는 소유주 차액 수납 기능이 없고, 공모 성공 통지도 자동 호출되지 않는다.
다음 작업이 끝나기 전에는 실제 수납 기능이 완성된 것으로 취급하지 않는다.

1. 공모: 성공 완료 시각 저장 및 통지 재시도 연결. SOLD_OUT/CLOSED 중 실제 성공 확정 지점을 공모 담당자가 정의해야 한다.
2. Wallet: 소유주 지갑 → 플랫폼 수납 계정으로 원금 이체. 잔액 부족 처리, 원장 기록, 중복 수납 방지 필요.
3. 정산: SALE_DEDUCTION의 매각대금 공제. 투자자 배당이 아닌 소유주 지급액에서 공제하며 부족분 처리 정책 합의 필요.
4. 수납 원장: 공모 ID 기반 중복 수납 방지, 확정 원금·이자·기준일·지갑 거래 ID 또는 정산 ID 보존.
5. 수납 완료 후 재공제 차단과 이자 종료 시각 기록. 현재 Asset의 견적 API만으로 자동 출금하지 않는다.
6. 지갑 선납 동결을 추가한다면 공모 실패/취소 시 해제 및 성공 확정 시 차감하는 보상 흐름 필요.

내부 API는 외부에서 직접 접근할 수 없도록 네트워크로 제한해야 한다.
SYSTEM 헤더는 신뢰된 내부 호출/검증된 Gateway가 설정하는 기존 프로젝트 방식을 전제로 한다.

## DB 적용

`V4__add_owner_burden_terms.sql`이 p_assets에 납부 방식, 공모 ID, 완료 시각, 확정 원금을 추가한다.
기존 레코드는 NULL 유지하며 과거의 이자나 선택을 소급 생성하지 않는다.
기존 자산을 전환하려면 소유주 선택을 받아 별도 승인된 데이터 이관 절차를 마련해야 한다.
